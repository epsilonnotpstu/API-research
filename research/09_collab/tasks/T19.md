# T19 — E5 code-mutation side: design + tool (write only)

R1 needs ground truth on both sides:
- **SPEC side:** `specmut` injects spec defects with a manifest.
- **IMPL side:** E5 must inject implementation defects into the SUT source, with an equally precise manifest. A pilot run can then check whether attribution labels an injected code fault as IMPL. This is the main missing piece of R1.

## What to build
1. **Operator catalogue** (`E5_codemut/OPERATORS.md`). Each operator has an expected L1/L2 and a conformance signal (which `conformance.py` violation kind should appear). At minimum:
   - `DROP_VALIDATION`: remove `@Valid`, `@NotNull` or an explicit guard. Expected I-ACCEPT-INVALID, or I-CRASH if invalid input reaches persistence.
   - `WRONG_STATUS`: change a documented status code in a handler or exception mapper. Expected I-RESP-CONTRACT / undocumented status.
   - `DROP_NULL_CHECK`: remove an existing null/absence check. Expected I-CRASH.
   - `RESP_FIELD`: rename or drop a serialized response field. Expected I-RESP-CONTRACT / RESPONSE_SCHEMA.
   - `REJECT_VALID`: add an over-strict guard. Expected I-REJECT-VALID / VALID_REJECTED.

   For each operator, list concrete candidate sites per SUT (`file:line`), found by reading the source. Prefer sites on operations that our runs actually reach; check `runs/<sut>/` exchanges.
2. **Tool** `E5_codemut/codemut.py`, stdlib only:
   - Applies one operator at one site to a **copy** of the SUT source tree. Never edit `_external/emb` in place.
   - Writes `<out>/patch.diff` and `<out>/manifest.json`. The manifest has: operator, sut, file, line, before/after snippet, affected operations as (path, method), expected_L1/L2, expected conformance signal, source sha256.
   - Has deterministic site selection by seed, plus an explicit `--site` option.
   - **Unit tests:** `E5_codemut/test_codemut.py` on small synthetic Java snippets. Do not test on real builds.
3. **Build and run plan** (`E5_codemut/README.md`):
   - Exact commands Claude will run: build the mutated copy in the same Maven container as the original builds, give the image a distinct tag, then run it through harness_v2.
   - **Harness changes:** you may not edit harness_v2. If code-mutant runs need harness support (for example a `SUT_JAR_OVERRIDE` or mutant image tag), write the exact proposed diff in the README for Claude to apply.
   - **Analysis:** how to pair a code-mutant run with its baseline, and how the existing `attribute.py` (fresh mode) and the triage relate to the manifest.
4. **Pilot selection:** propose 2–3 mutants per SUT for the first batch, with your reasoning.
