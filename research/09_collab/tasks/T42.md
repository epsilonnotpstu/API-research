# T42 — Feasibility: mining real spec↔code "contract-alignment" fixes with known direction (Codex, offline mining)

Read `09_collab/PROTOCOL.md` first. Effort: xhigh.

## Why
E4 (`08_experiments/E4_triage/E4_RESULTS.md`) found that zero-shot LLM triage (macro-F1 0.94) beat the codebook-v0.6 procedure (0.66–0.70) on **artificial** injected faults, and the real-item evidence is thin (22 decoys).

The future-version oracle (T41) yielded only 3/62 directions for our own SUTs. Before any claim about triage methods, we need a **real-defect benchmark** in which the truth is the developer's own fix direction:
- a commit that resolved a spec↔code mismatch by changing the **contract** (spec file, or contract annotations such as `@Operation`, `@ApiResponse(s)`, `@Schema`, `@Parameter(required)`, springfox `@Api*`) → truth **SPEC**;
- one that changed **behaviour** (handler, validation, DTO serialization, exception mapping) to honour the existing contract → truth **IMPL**;
- one that changed both, for the same proposition → **BOTH**.

This task measures the **feasibility and yield only**. It does not build the blind package yet.

## Steps
1. **Per repo, identify contract surfaces:**
   - checked-in OpenAPI/Swagger files (yaml/json with a top-level `openapi`/`swagger` key);
   - annotation-based contract (springdoc/springfox/JAX-RS swagger annotations);
   - generated-spec-only setups.

   Also identify the behaviour surfaces: controllers/resources, DTOs with Jackson/validation annotations, exception handlers.
2. **Candidate commits.** Use a deterministic heuristic, documented in the report. For example, commits that touch a contract surface and/or a behaviour surface **of the same operation** within one commit or a short window, plus commit-message cues: `swagger`, `openapi`, `api doc`, `spec`, `contract`, `documentation`, `required`, `status code`, `response code`, `nullable`, `match`, `align`, `fix`, `correct`. Exclude merges, mass reformatting, dependency bumps and new-endpoint additions.
3. **Manual review of candidates.** Review at least 60 in total, spread across the repos. For each one, decide whether it **resolves a specific pre-existing mismatch** between contract and behaviour for an existing operation. Not acceptable: adding a new feature with its docs, or changing both to new behaviour.
   - For accepted ones, record:
     - `repo, fix_commit, parent_commit, date, operation (method + path/template), proposition`;
     - `truth_direction` (SPEC/IMPL/BOTH);
     - `evidence` (file:line in parent and in the fix, with the diff hunk ref);
     - `message_excerpt` (≤160 chars);
     - `confidence` 1–3;
     - `contract_kind` (spec_file / annotations).
   - **The proposition must be written from the PARENT (pre-fix) state only**, in a fixed neutral template: `"<METHOD> <path>: contract says <X>; implementation does <Y>"`. It must not mention which side was later changed. Also write `proposition_check` = which parent-side locators support X and Y.
4. **Yield and balance:**
   - accepted items per repo and per direction;
   - acceptance rate of the heuristic;
   - time and effort notes;
   - how many items would need runtime traffic, versus static-only judgment being feasible.
5. **Threats.** Cover at least:
   - regenerated specs;
   - annotation drift;
   - squash merges;
   - "fix" that is really a feature;
   - ⚠️ LLM memorisation risk for popular repos and commits (note stars/popularity);
   - leakage through future files if a package were built from the parent snapshot (e.g. CHANGELOG mentioning the later fix).
6. **Recommendation:** is a ≥40-item, reasonably balanced (SPEC vs IMPL) real benchmark achievable from these repos? If not, what repo selection criteria would get there?
