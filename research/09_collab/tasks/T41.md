# T41 — Future-version oracle: did upstream later fix the SPEC or the CODE? (Codex, offline mining + analysis)

Read `09_collab/PROTOCOL.md` first. Effort: xhigh.

## Why
E4 (`08_experiments/E4_triage/E4_RESULTS.md`) showed that every evaluation so far rests on either:
- artificial injected faults, or
- adjudicated labels produced by our own LLM + supervisor pipeline.

We need **real developer evidence of fix direction**. Here is the idea:
- Take a baseline mismatch between the deployed spec and the deployed code.
- If a later upstream version changed the **spec** to match the code's behaviour, that is evidence for SPEC.
- If it changed the **code** to match the spec, that is evidence for IMPL.
- If it changed both, that is evidence for BOTH.

This is the codebook's E-DEV / E-HISTORY evidence, but from the real project history.

## Steps
1. **Anchor:** for each SUT, find the upstream commit(s) whose tree best matches the EMB snapshot.
   - Match per-file blob hashes of the relevant source and spec files.
   - Report the matching fraction and any EMB-local modifications. EMB sometimes patches SUTs: list the differing files.
   - ⚠️ If no good anchor exists (match < ~80% of relevant files), report this and continue with the closest commit, flagging lower confidence.
2. **Locate the deployed spec's upstream source:**
   - petstore: `src/main/resources/openapi.yaml` or similar;
   - cwa: `api-docs.json` or a springdoc-generated spec;
   - market: springfox/annotation-generated?

   If the spec is **generated from code annotations**, then spec changes are code changes. In that case classify changes to annotations versus handler logic separately, and say so explicitly.
3. **For each baseline item (62):**
   - Identify the concrete mismatch proposition: operation, status/field/constraint, and direction. Use the item's representative exchange or labeller evidence; do not change labels.
   - Search the upstream history **after the anchor** for commits touching:
     - (a) the spec element;
     - (b) the handler / DTO / validation / exception mapping.
   - Decide:
     - `fix_direction` ∈ {`spec_changed_to_match_code`, `code_changed_to_match_spec`, `both_changed`, `unchanged_at_head`, `changed_unrelated`, `unclear`};
     - commit locators (`full_sha:path:line` or diff hunk), the date, and the commit message excerpt (≤ 160 chars);
     - for `unchanged_at_head`: the HEAD state.
   - **Mark ⚠️ when the change could be incidental** (refactor, version bump) rather than a fix of this mismatch.
4. **Compare** the derived developer direction with `final_L1`, for items with a non-`unchanged`/`unclear` direction:
   - spec_changed ↔ SPEC / SPEC_PARTIAL;
   - code_changed ↔ IMPL;
   - both ↔ BOTH.

   Report the agreement table and every disagreement. Do **not** rewrite labels; produce review proposals only.
5. **Yield:** how many items get usable developer evidence? Discuss whether this oracle could scale (E6), and its threats:
   - survivorship;
   - spec regeneration;
   - squash commits;
   - archived repos.
