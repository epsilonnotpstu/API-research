# T22 — E5 noise floor: control-vs-control mode (write only)

E5 fresh analysis shows large changes on NON-mutated operations (`e5_summary.csv`):
- scout: up to 9 NEW and 27–52 INCREASED/DECREASED per seed.
- petstore: 0–5 NEW and 7–15 INCREASED/DECREASED.

To interpret a mutant's signal we need the same metrics for two runs of the **same control image with the same seed**.

## Deliver (in `08_experiments/E5_codemut/`, excluding `work/` and `blind_key.csv`)
1. **`run_noise.sh MUT_DIR [SEEDS…]`.** Runs the control image twice per seed via `harness_v2/run_pilot.sh`, as roles `control` and `control_repeat`.
   - Use exactly the settings of `run_pair.sh`.
   - Write a separate ledger, `MUT_DIR/noise-runs.tsv`. The existing pair ledger stays untouched.
   - If `harness_v2/run_pilot.sh` or `run_metadata.py` would need a change to accept a second control role, **do not edit them**. Prefer reusing `CODE_ROLE=control` with distinct run IDs. If a harness change is unavoidable, write it as a proposed diff, as in T19.
2. **`validate_pair.py`: a noise mode.** Same image, jar and source expected on both sides. Reuse all the T20/T20b/T20c rules.
3. **`analyse_noise.sh MUT_DIR`.** The same fresh analysis, with control as "baseline" and control_repeat as "treatment". Output: `MUT_DIR/noise-analysis-s<seed>-<oracle>/`.
4. **`summarise_e5.py`: noise rows** (`kind=noise`), with the same columns, and specifically the counts on the operations that the manifest marks as mutated. This tells how often a *non-mutated* build shows NEW, INCREASED or DECREASED on those ops by chance.
   - Add a derived column per pair: `signal_exceeds_noise`, with a stated rule. For example: the mutant's expected-kind NEW/INCREASED on mutated ops is present, while the same fingerprint is absent in all noise repeats for that seed.
5. Tests for the new code. Re-run all E5 tests.
6. Bengali `09_collab/reports/T22_report.md`, plus a Log line.
