G2 reviewed all 138 items in `items.csv` order: 102 YES, 32 NO, and 4 UNCLEAR. All item folders were accessible. Only supplied package material was used; no item code, network access, or repository history was used. Locators refer to the packaged filenames and their actual line numbers.

The four unresolved relevance decisions are:

- **A033:** The advisory describes cross-account address disclosure, but the supplied source and patch concern publication comments and enforcing POST. The patch does not demonstrate the reported address-ownership check.
- **A080:** The advisory describes public like inflation; the patch exclusively changes OAuth redirect validation. These point to different vulnerability classes under the task's exclusions.
- **A133:** The before-version already rejects differing object and template metadata. The patch replaces that rejection with metadata normalization; the advertised scope-widening exploit is not established by this before/after pair.
- **A100:** The advisory's wording does not clearly identify the unauthorized caller or action. Adding a comment service interface suggests interception changes, but the material does not show the policy decision sufficiently to classify the flaw confidently.

Other difficult cases:

- **A039:** The patch intentionally retains inherited administrator access. The supported correction concerns an inherited write grant overriding a nearer read grant; the advisory's administrator example is not fully remediated by this patch.
- **A046:** The supplied fix keeps likes public and adds rate limiting and duplicate suppression. Classified NO for the demonstrated metric/resource-abuse remediation, rather than assuming anonymous likes must require authentication.
- **A103:** The advisory establishes unauthorized S3 bulk deletion, but the only supplied patch changes test-client setup. Marked YES with reduced confidence and OTHER for fix location. **A112** likewise relies on the explicit advisory for the original exposure: its patch adds query-token support to pre-existing authentication checks, rather than demonstrating installation of those checks.
- **A127:** The before-version already checks the project for single-resource GET. The remaining supplied change checks multiget REPORT hrefs; the coding describes that narrower supported path.
- **A051, A060, A071, A138:** Restricted-component and verification permissions are HTTP-accessible authorization boundaries. A138 removes the Restricted permission mechanism rather than adding a replacement check; its classification describes the pre-fix policy violation.
- **A028:** Treated as incorrect attribution of an authenticated certificate to an RBAC principal, rather than a cryptographic signature-validation flaw. **A052** checks possession of deduplicated content to prevent cross-repository disclosure. By contrast, signature/token validation and recovery cryptography were excluded where they are the actual mechanism.
- **A058** gates an already-authenticated credential-deletion operation by assurance level. **A121** checks the target of an ordinary account update, rather than a password-reset flow. **A135** explicitly restricts an administrator-only property; downstream SSRF is not the basis for its access-control classification.
- **A019, A047, A119** demonstrate only bidirectional/ordinary gRPC RPCs, with no supplied HTTP API mapping. **A116** is included because the contract explicitly exposes POST `/v3/watch`. WebSocket endpoints reached by HTTP upgrade were treated as HTTP-reachable, with their returned protocol messages as black-box observations. A099 explicitly confines its flaw to WebRTC input and excludes HTTP/WebSocket controls.
- Network-policy, container-group, local PostgreSQL, and controller-only flaws were excluded when no affected HTTP operation of the service was established. A136 concerns permissions enforced by the Karmada control-plane API; generating those permissions through a CLI does not make the impact CLI-only. A106 concerns the local CLI development configserver and was excluded.

Contract limitations affect several rows. UNCLEAR denotes an operation or applicable security requirement that could be lost to truncation; it does not assert that the complete upstream contract lacks it. DECLARED requires evidence of an applicable requirement and a defined scheme. A089 names `ApiKeyAuth` but supplies no scheme definition, so security is UNCLEAR although the operation expresses authentication intent. Scope requirements in A061 and the admin scope on A031's import operation state specific violated rules; a bare login requirement does not establish an unrelated owner, tenant, or role policy.

The NiFi files and OpenRemote base file contain security/metadata scaffolding without operations and were treated as NO_CONTRACT. A014 lists the affected path but delegates its method to a missing external reference, so operation coverage is UNCLEAR. A053's supplied contract documents file download but omits the exact `/info` operation changed by the patch; that operation is ABSENT. Contracts for unrelated subservices, REST-only contracts for Git/CalDAV endpoints, and an S3 gateway's neighboring management REST operation do not establish coverage of the vulnerable operation.

Principal counts describe credentials needed by the attacker/test comparison, with target resources and relevant configuration supplied as fixtures. NONE includes dummy bearer strings that do not identify any valid principal. ONE covers self-escalation or forbidden-property updates. Revocation and role-comparison tests generally use TWO_ROLES; ownership and tenant comparisons generally use TWO_SAME_ROLE. A078, A097, and A101 leave the principal requirement UNCLEAR because the supplied material does not specify the deployment's authentication/policy setup.
