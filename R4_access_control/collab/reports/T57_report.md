## Material issues ও দুই implementation-এর ফল-বদলানো পার্থক্য

1. **M01 — candidate parsing ও repository preference।** Primary ordinary `https://github.com/o/r` source location-এ stable ordering ঠিক রাখে। কিন্তু `https://github.com/o/r.git` বা `/tree/...` হলে repository identity না বুঝে whole string compare করে; preferred repository পিছিয়ে যেতে পারে (`r4p.py:117–124`)। Independent repository extract করে (`r4_resolve.py:15–26`), যা plan-এর repository match অনুসরণ করে। Primary regex 40 hex-এর পরে `xyz` থাকলেও prefix candidate বানায়; independent তা প্রত্যাখ্যান করে। Primary whitespace trim করে, independent করে না; padded URL গ্রহণের policy plan নির্ধারণ করেনি। দুটো regex-ই T56b-এর 7-character minimum নেয়; plan-এর “or shorter hex” আক্ষরিকভাবে 1–6-ও বোঝালে দুটোই সেই interpretation cover করে না।

2. **M02 — first API resolution বনাম first successful fetch।** Primary full-SHA candidate API ছাড়াই নেয় এবং failed candidate fetch-এর পরে পরের candidate চেষ্টা করে (`r4p.py:138–151`)। ফলে first API-resolvable commit অন্যটি হলেও different fix বাছতে পারে। Independent first API resolution-এই choice স্থির করে (`r4_resolve.py:68–90`); plan §3.38 অনুযায়ী এটিই সঠিক। Short-SHA `.sha` extraction বনাম JSON extraction নিজে কোনো substantive difference নয়।

3. **M03 — failures/retries ভিন্ন ফল দেয়।** Primary short-SHA API retries exhausted হয়ে `None` হলে `err=True` না করে continue করে, শেষ পর্যন্ত `NO_COMMIT` দিতে পারে (`r4p.py:139–140,154`); synthetic probe-তে সেটিই হয়েছে। Primary nonzero fetch failure retry করে, কিন্তু subprocess timeout loop-এর বাইরে উঠে যায়; resolver তখন subsequent candidate নিতে পারে, collector/build বন্ধ হতে পারে। Independent timeout/OSError-ও retry করে এবং uncertain API/fetch failure-এ `FETCH_ERROR` দেয়। API 404/422 সব candidate-এ হলে independent `NO_COMMIT`; primary full SHA fetch failures-কে `FETCH_ERROR` বলে। Plan/T56b-এর genuine absence বনাম network failure distinction independent ভালো রাখে। Timeouts/backoff/default durations-ও আলাদা: primary 600s/collection 1800s ও 2,4s; independent 300s ও 1,2s।

4. **M04 — F1 repair সঠিকভাবে যোগ হয়েছে, কিন্তু failure distinction অসম্পূর্ণ।** `have_commit` true হলেই parent আছে ধরে নেয় না: `r4p.py:146–149` ঠিকভাবে re-fetch করে। তাই “F1 implement হয়নি” বলা ভুল। কিন্তু repair fetch ব্যর্থ হলে return value উপেক্ষা করে parent lookup ব্যর্থতাকে `NO_PARENT` বানায় (`r4p.py:148–150`)। Synthetic failure-এ `NO_PARENT` হয়েছে। Independent refetch failure→`FETCH_ERROR`; refetch-এর পরেও shallow marking থাকলে raw header থেকে first parent নিয়ে object verify করে। True root-এ দুটোই `NO_PARENT` দিতে পারে। Current `resolved.json`-এ `NO_PARENT` count 0; repair failures বাস্তবে ঘটেছে দাবি করছি না।
